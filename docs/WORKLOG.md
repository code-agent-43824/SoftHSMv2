## 2026-08-20 — правки по третьему отчёту: даты, события слотов, имя токена

**План.** Владелец прислал третий отчёт — трассировку трёх потребителей
библиотеки: Рутокен Плагин, `ra.rutoken.ru` и Центр управления Рутокен. Из
семи пунктов он назначил четыре: починить атрибуты, которые хранятся
зашифрованными; сделать `C_WaitForSlotEvent` — причём для форка целиком, а не
только для профиля; VKO не делать, а написать по нему передачу другому агенту;
шифрование не делать.

**Сделано.**

- **`CKA_START_DATE` / `CKA_END_DATE` на приватных объектах.** Оба
  переопределения `updateAttr` клали значение мимо шифрующего базового метода,
  и любое чтение потом падало с `CKR_GENERAL_ERROR`. Теперь пишут через базовый
  метод. Хранилища, где даты уже лежат открытым текстом, продолжают читаться:
  шифртекст короче `CK_DATE` не бывает, так что старое значение опознаётся по
  длине без догадок. Дефект апстримный, воспроизведён с выключенным профилем.
- **Блокирующий `C_WaitForSlotEvent`** для форка целиком. Ожидание на
  `std::condition_variable` в состоянии, которое переживает `C_Finalize`;
  событие поднимается там, где оно в SoftHSM действительно есть, — при
  `C_InitToken` на запасном слоте. Подробности в `JOURNAL`.
- **`C_EX_GetTokenName`** — двухпроходно, при включённом профиле. Центр
  управления зовёт её сразу после `C_EX_GetTokenInfoExtended` и при отказе
  закрывает сессию.
- **`docs/HANDOFF-VKO.md`** — передача задачи по VKO: что именно запрашивает
  плагин, где отказ, чего не угадывать, чем проверять, как воспроизвести.
- **Сквозной гейт** получил третий режим, `core-behaviour`: он гоняется с
  выключенным профилем, потому что проверяет не Рутокен, а обычный PKCS #11.
  Даты, события слотов, и — через `P11_TEST_STORE_DIR` — то, что дата
  приватного ключа не лежит в файлах хранилища открытым текстом. Последнее
  оказалось единственным способом поймать дефект: миграционная поблажка
  маскирует его через API. Проверено отрицательным прогоном.
- **`rutoken-reference-dump`** дополнена: сплошной обход вендорских атрибутов
  `0x80003000`..`0x80003012`, `0x8000800D/E` по одному с запросом размера,
  вендорские атрибуты сертификата и `C_EX_GetTokenName`. Собрана под Windows
  x64 для владельца.

**Дальше.** Значения `0x80003010`, `0x8000800E` и `0x80000009` с устройства,
затем этап 7 — юнит-тесты на ГОСТ 2012. VKO — отдельной задачей.

## 2026-08-20 — объект аппаратной особенности (P1-A)

**План.** Владелец снял утилитой одиннадцать атрибутов
`CKO_HW_FEATURE` / `CKH_VENDOR_TOKEN_INFO` с эталонного устройства. Отдавать
из профиля ровно это — иначе пять методов Рутокен Плагина отвечают ошибкой.

**Сделано.** Объект синтезируется, пока профиль включён: находится поиском по
`CKA_CLASS` и `CKA_HW_FEATURE_TYPE` (и пустым шаблоном, как на устройстве),
отдаёт одиннадцать значений устройства, читается без входа по PIN, не
меняется и не удаляется. Длины совпали с устройством: булевы — один байт,
остальные — `sizeof(CK_ULONG)`, четыре байта на Windows. Вопрос про
недокументированный `0x8000800D` закрыт: устройство отдаёт один байт со
значением 0. Гейт `rutoken-profile` дополнен проверкой — она спрашивает так
же, как плагин (один вызов, буферы заранее), включая восьмибайтовый буфер под
не-булев атрибут; проверено отрицательным прогоном: подменённое значение гейт
валит. Названия `TOKEN_INTERFACE_NFC/BLUETOOTH/ISO` из `rutoken.h` убраны —
они были догадкой, и устройство её не подтверждает: в маске `0x21` второй бит
ими не объясняется.

Попутно закрыта дыра в пуш-CI: он гонял гейт только на свежем хранилище, а на
неинициализированном токене SoftHSM не открывает сессию, так что новая
проверка там не запускалась бы вовсе. Добавлен второй прогон на
инициализированном токене с меткой — полсекунды работы, и заодно ветка правила
о метке перестала быть только релизной.

**Дальше.** Этап 7 — юнит-тесты на ГОСТ 2012.

## 2026-08-14 — полная сборка продукта после каждого изменения в транке

**План.** Владелец хочет, чтобы портируемый продукт собирался целиком после
любого изменения в `main`, автоматически, следом за зелёным основным CI.

**Сделано.** Проверил историю: `portable-release.yml` был
`workflow_dispatch`-только во всех 27 своих ревизиях, с самого первого коммита
— автозапуска не было никогда и ничего не отключалось. Добавлен триггер
`workflow_run` на успешное завершение `CI` в `main`. Автоматический прогон
собирает и проверяет все шесть платформ и на этом останавливается; публикует
релиз по-прежнему только ручной запуск с тегом. Во всех тринадцати `checkout`
проставлен `ref: github.event.workflow_run.head_sha` — иначе собирался бы не
тот коммит. Новый автоматический прогон вытесняет предыдущий.

**Дальше.** Этап 7 — юнит-тесты на ГОСТ 2012.

**Сделано.** Релизный workflow пушем не запускается по устройству — у него

хранилище. Последовательность проверена локально сборкой GCC 9 — той же
версии, что в контейнере `ubuntu:20.04` у раннера.
