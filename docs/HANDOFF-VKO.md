# HANDOFF — ГОСТ-расшифрование после VKO/KEG

Обновлено: 2026-08-21. Первый этап закрыт; это передача следующего шага.

## Что уже сделано

Фактический вызов Рутокен Плагина из `spy-decrypt.log` реализован:

- механизм — `CKM_GOST_KEG` (`0xD4321039`), а не
  `CKM_GOSTR3410_12_DERIVE` (`0xD4321007`);
- параметры — стандартная `CK_ECDH1_DERIVE_PARAMS`: `CKD_NULL`, 32 байта
  синхропосылки и 64 байта открытого ключа второй стороны в форме little-endian
  X‖Y;
- базовый объект — приватный `CKK_GOSTR3410` с `CKA_DERIVE = CK_TRUE`;
- результат — 64-байтовый секретный `CKK_MAGMA_TWIN_KEY` (`0xD4321007`).

Имена, значения и ABI подтверждены официальными заголовками, примерами и
документацией Рутокен. Совпадение численного значения механизма
`CKM_GOSTR3410_12_DERIVE` и типа ключа `CKK_MAGMA_TWIN_KEY` нормально: это
разные пространства констант.

`BotanGOST2012KEG` выполняет VKO-2012/256, затем
`KDF_TREE_HMAC_Streebog256` с меткой `kdf tree`, двумя блоками и seed из
байтов 16..23 синхропосылки. Ключевой материал очищается после записи объекта.
`C_DeriveKey` строго проверяет длины, KDF, тип базового и выходного ключей,
запрещает входной `CKA_VALUE` и принимает `CKA_VALUE_LEN` только со значением
64.

Сквозной тест `verifyGOSTKEG` в
`tests/portable/portable-token-e2e.cpp` проверяет все 64 байта независимого
контрольного результата, повторяет точный трёхатрибутный выходной шаблон
плагина и проверяет отрицательный случай KDF.

## Важная ловушка Botan 2.19.5

Botan 2.19.5 сопоставляет OID
`id-tc26-gost-3410-2012-256-paramSetA` со старой CryptoPro-A, хотя это разные
кривые. KEG использует настоящую TC26 paramSet A с cofactor 4. Для этого OID
группа построена из явных параметров в `BotanGOST2012KEG.cpp`; арифметика и
ослеплённое умножение по-прежнему выполняются Botan. Не заменять эту группу на
`Botan::EC_Group(encodedOID)`, пока поставляемая версия Botan не исправлена и
это не доказано контрольным результатом.

Вторая ловушка — порядок байтов UKM. KEG разворачивает первые 16 байт, а VKO
интерпретирует полученное little-endian; для передачи в big-endian `BigInt`
две перестановки взаимно уничтожаются. Нулевой UKM обрабатывается отдельно по
правилу KEG.

## Точный следующий шаг

Повторить расшифрование на `ra.rutoken.ru` через Рутокен Плагин 4.12.2.0 и
`pkcs11-spy`. `C_DeriveKey` должен вернуть `CKR_OK`; сохранить все следующие
PKCS #11-вызовы до первого отказа, включая полные механизм, параметры и шаблон
объекта.

По прежней трассе нельзя доказать, что дальше будет именно `C_UnwrapKey` и
какой симметричный механизм выберет плагин: выполнение раньше останавливалось
на KEG. Поэтому следующий этап реализовывать только по новой трассе. До неё не
трогать `C_UnwrapKey`, `C_Encrypt` и `C_Decrypt`.

Стенд и подмена библиотеки остаются прежними: `pkcs11-spy.so` под именем
`librtpkcs11ecp.so` рядом с приложением, которое загружает его через RPATH
`$ORIGIN`. Для сценария нужна обменная ключевая пара с `CKA_DERIVE = CK_TRUE`
и сертификат на неё; материалы `mkderive.c`, `mkcert.py` и Playwright-сценарий
были приложены к третьему отчёту владельца.
