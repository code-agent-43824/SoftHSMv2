## 2026-10-03 — прогон пробы на эталонном устройстве: ответы сняты

**Повод.** Владелец прогнал `tests/portable/rutoken-device-probe.c` на живом
токене (серийный `1217688090`, «Рутокен ЭЦП 3.0 3127 USB», библиотека Актив,
`--write --format`) и прислал `probe.log`. Это **первая трасса с устройства**
по этим вопросам; раньше были рассуждение, стандарт и программный стенд.
Бинарник совпал с нашей сборкой из `259baad6` по SHA-256.

**Что показало устройство.**

- **`utcTime` — 16 нулевых байт**, не пробелы. `CKF_CLOCK_ON_TOKEN` снят. У
  нас туда пишется текущее UTC-время — надо заполнять нулями.
- **Память реальна и расходуется.** `ulTotalPublicMemory =
  ulTotalPrivateMemory = 131072`, свободно одинаково в публичном и приватном
  поле. Каждый объект `CKO_DATA` на 2048 байт отъедал ~2176 байт; на 40-м
  объекте — `CKR_DEVICE_MEMORY`, после удаления всех память вернулась
  (87072 → 704 → 86464). То есть при исчерпании устройство отвечает
  `CKR_DEVICE_MEMORY`, поля памяти `C_GetTokenInfo` равны полю расширенных
  сведений. У нас всё это — константа.
- **KEG на 512 битах работает на устройстве.** Две сгенерированные на токене
  пары сходятся к одним 64 байтам и для 256, и для 512. Принимаются **два**
  типа twin-ключа — `CKK_MAGMA_TWIN_KEY` и `CKK_KUZNECHIK_TWIN_KEY`, и дают
  **одни и те же** байты (ярлык разный, значение одно — как и писали);
  `CKK_GENERIC_SECRET` устройство отвергает `CKR_TEMPLATE_INCONSISTENT`. У нас
  принят только MAGMA. Пары ключей устройство делает лишь токенными:
  сессионные (`CKA_TOKEN=false`) — `CKR_TEMPLATE_INCONSISTENT`.
- **Генерация идёт на всех наборах параметров.** 256 paramSetA/B/C и 512
  paramSetA/B/C — все `CKR_OK`. У нас 512 B/C и 256 C при генерации
  отвергаются; трасса на расширение теперь есть.
- **Импорт сырого закрытого ключа отвергается** (`CKR_TEMPLATE_INCONSISTENT`,
  оба порядка байт) — как и ожидалось для железа; эталоны TC26 на устройстве
  через импорт не воспроизвести.
- **`CKM_GOSTR3410(_512)` с OID хеша в параметре** —
  `CKR_MECHANISM_PARAM_INVALID`, без параметра подпись идёт. Наша граница
  совпала с устройством.
- **Журнал непустой читается.** `C_EX_GetJournal` отдаёт данные (224, затем
  126 байт), запись — TLV с тегами `0x80` (запись), `0xAA` (хэш), `0xB6`
  (подпись), `0x85`, `0x83`; хвост записи содержит счётчик подписей BE32 и ID
  токена. Формат совпал с разбором `JournalParse.c` из
  `code-agent-43824/opensc`. Сырьё — в `probe.log`.
- **Признак «PIN не заводской» — по значению.** На заводских PIN (как
  получено) `ADMIN_PIN_NOT_DEFAULT=0`, `USER_PIN_NOT_DEFAULT=0`; после
  `C_SetPIN` на другой PIN `USER_PIN_NOT_DEFAULT=1`; после смены **обратно на
  заводское значение** флаг снова `0`. То есть устройство сравнивает PIN с
  заводским значением, а не просто «менялся ли». В `C_GetTokenInfo` на
  заводском PIN стоит `CKF_USER_PIN_TO_BE_CHANGED` и снимается после смены.
  Это подтверждает решение владельца 29.09.
- **Короткий PIN — `CKR_PIN_LEN_RANGE` везде, включая 3 символа.** `C_SetPIN`,
  `C_InitPIN` и `C_InitToken` с PIN короче 6 отвечают `CKR_PIN_LEN_RANGE`,
  в том числе на 3 символа. У нас `C_InitToken` на 3 символа даёт
  `CKR_PIN_INCORRECT` из-за ранней проверки `MIN_PIN_LEN = 4` — её надо
  убрать, чтобы «короче 6» всегда давало `CKR_PIN_LEN_RANGE`. `C_Login` c
  3–5 символами — `CKR_PIN_INCORRECT` и **тратит попытку** (10 → 9 → 8 → 7);
  наше поведение совпало.
- **Счётчик попыток: 10/10, −1 за попытку.** `CKF_USER_PIN_FINAL_TRY` на
  остатке 1, `CKF_USER_PIN_LOCKED` и `ulUserRetryCountLeft = 0` на 0, 11-я
  попытка — `CKR_PIN_LOCKED`; `C_EX_UnblockUserPIN` под SO сбрасывает в 10.
  SO: одна неверная 10 → 9, верный вход сбрасывает. Это **опровергает**
  числа программного стенда 28.09 (`retryLeft = 2`, не убывал): на устройстве
  обычный убывающий счётчик. Наше поведение `.53`/`.54` совпало с устройством.
- **Смена PIN действует сразу во всех процессах.** Процесс A вошёл, процесс B
  сменил user PIN; у A операция с закрытым объектом в уже открытой сессии —
  `CKR_USER_NOT_LOGGED_IN` (устройство сбросило вход), свежий вход старым PIN —
  `CKR_PIN_INCORRECT`, новым — `CKR_OK`. Это **прямо противоположно** нашему
  модулю, где A до перезапуска принимает старый PIN. Подтверждает, что копию
  PIN в `Token` надо сверять с состоянием токена на момент `C_Login`.

**Чего проба не сняла.** `C_EX_InitToken` во всех вызовах вернул
`CKR_ARGUMENTS_BAD` — вендорская библиотека не приняла наш вызов с
`CK_RUTOKEN_INIT_PARAM` (вероятно, иной способ передачи SO PIN или
UseRepairMode). Поэтому форматирование через PKCS #11 осталось непроверенным;
владелец форматирует токен штатно через `rtadmin format … repair` (лог
`rtadmin-format.log`). Контракт `C_EX_InitToken` требует отдельного разбора
вызова. Разрушающего форматирования проба на устройстве не сделала.

**Наблюдение по флагам.** На этом устройстве базовые `flags` расширенных
сведений — `0x1C02` (нет `ADMIN_CHANGE_USER_PIN = 0x01`); наша константа
профиля этот бит ставит, а эталон 14.08 («5100 Flash») давал `0x1C0F`. Флаги
разнятся по модели; профиль повторяет эталон 14.08 — трогать без решения
владельца не будем (это «Settled decisions»).

**Вывод.** Почти все открытые вопросы закрыты трассой: `utcTime` — нули,
память расходуется с `CKR_DEVICE_MEMORY`, KEG-512 работает и принимает оба
twin-типа, короткий PIN — `CKR_PIN_LEN_RANGE`, счётчик обычный, смена PIN
мгновенна во всех процессах, формат журнала снят. Правки модуля по этим
данным — отдельными задачами (PLAN).

## 2026-09-30 — решения владельца 29.09 по `FAKE_RUTOKEN_ECP` и сверка с `.54`

**Повод.** Владелец 29.09 принял решения для совместимости с ПО для

  `Token::Token`; счётчик же с `.53` читается и меняется в транзакции.

  остаток 10 → 9 → 8 → 7.
- `rutoken-reference-dump.c` поле `utcTime` не выводит. Существующий
  клиент не снимает KEG-512 с устройства: этот путь идёт через импорт

**Решения владельца 29.09.** Смена PIN должна действовать сразу во всех
процессах, как на устройстве. Заводские PIN (`12345678`/`87654321`) не

Свободная память должна меняться; модель — за владельцем. `utcTime` —
пустое, байт заполнения снять с устройства. KEG на 512-битных ключах может
работать на эталоне — снять пробой. Журнал — отдельной задачей. Не менять:
пустые описания незанятых слотов фасада, счётчики сессий в
`C_GetTokenInfo`, список механизмов с нереализованными.

## 2026-09-30 — у гонки с `C_Finalize` две стороны: зависание и падение

**Гипотеза.** Гонку 29.09 закрывает флаг «библиотека открыта» под замком
событий: тогда проверка инициализации и запоминание `epoch` атомарны
относительно `endSlotEventEpoch()`.

**Что сделали.** До правки написали регрессионный тест
`InfoTests::testWaitForSlotEventFinalizeRace`: 2000 раз `C_Initialize`,
блокирующий `C_WaitForSlotEvent` в потоке, сразу `C_Finalize`.

**Что показала проверка.** На коде без правки тест провалился во всех 12
прогонах: 9 раз вызов не вернулся (потерянное пробуждение), 3 раза
процесс упал. Core-дамп: в потоке ожидания
`SoftHSM::C_WaitForSlotEvent (this=0x0)` на проверке `isInitialised` —
`main.cpp` берёт объект через `SoftHSM::i()`, а `C_Finalize` в это время
сбрасывает его через `SoftHSM::reset()`, и поток получает null. Один флаг
под замком от падения не спасает: до замка вызов не доходит.

**Вывод.** `C_WaitForSlotEvent` не должен касаться объекта `SoftHSM`.
Точка входа стала статической (`SoftHSM::waitForSlotEvent`), и весь ответ
решается под замком событий по флагу `open`. После правки тест прошёл
10 прогонов подряд, харнесс — 3 × 50 000 итераций. Цена: этот путь не
проходит проверку `fork`, которую делает `SoftHSM::i()`: при
`library.reset_on_fork` вызов в дочернем процессе до его собственного
`C_Initialize` ответит так, будто библиотека открыта (по коду, не
проверялось).

## 2026-09-29 — счётчик нельзя обновлять из кеша разных процессов

**Гипотеза.** Достаточно записывать остаток через обычный атрибут

**Проверка и вывод.** `ObjectFile::setAttribute` сериализует запись файла,

в ноль, остальные не получили дополнительной попытки. Это программная
проверка, не испытание физического устройства.

**Совместимость.** Архив продукта `.52` создал токен с прежним PIN длины 4;
новый модуль открыл его, принял этот PIN, после одной ошибки показал точный
остаток 9, после успешного входа — снова 10. Новая граница 6–32 проверяется
при установке PIN, не при чтении уже существующего.

## 2026-09-29 — гонка `C_WaitForSlotEvent` с `C_Finalize` воспроизведена

**Гипотеза.** `SoftHSM::C_WaitForSlotEvent` читает `isInitialised`, и лишь
затем `awaitSlotEvent` берёт замок `slotEvents()`. Если `C_Finalize` из
другого потока целиком выполнит `endSlotEventEpoch()` (бампит `epoch`,
`notify_all` — но ждущего ещё нет) между этими двумя шагами, ожидающий
запомнит уже увеличенный `epoch` и уснёт на `state.changed.wait` до
следующего `C_Finalize` или события — потерянное пробуждение.

**Что сделали.** Отдельный харнесс (`scratchpad`, в репозиторий не входит)
на обычном модуле `build/src/lib/libsofthsm2.so`: в цикле `C_Initialize`,
поток с блокирующим `C_WaitForSlotEvent(0,…)`, сразу `C_Finalize` в главном
потоке без задержки, сторож 0.4 с на возврат потока. Обычный модуль,
системный OpenSSL 3.0.13.

**Что показала проверка.** Зависания на итерациях 0, 408, 450, 1794 —
порядка одного на сотни-тысячи итераций при нулевой задержке. gdb на
зависшем процессе: поток стоит в `awaitSlotEvent` на
`state.changed.wait` (`src/lib/SoftHSM.cpp:202`), а главный поток уже
вернулся из `C_Finalize`. Прочие итерации возвращают `400`
(`CKR_CRYPTOKI_NOT_INITIALIZED`) — штатный путь, когда `endSlotEventEpoch`
успевает после регистрации ждущего. Значит, `epoch` защищает только от
`C_Finalize` **после** захвата замка ждущим, но не от полностью прошедшего
до него.

**Вывод.** Гонка реальна и специфична для форка (блокирующая форма — его
добавление). В сервисном тесте `InfoTests::testWaitForSlotEvent` окно
закрыто 50 мс между стартом потока и `C_Finalize`, поэтому там она почти
недостижима, но на нагруженном раннере тест может изредка виснуть, а живой
watcher-поток с `C_Finalize` при остановке — тем более. Отдельно замечен
более общий, апстримный след: `SoftHSM::i()` и чтение `this->isInitialised`
на входе не синхронизированы с `SoftHSM::reset()` в `C_Finalize` (гонка за
`instance` и возможный доступ к разрушенному объекту); блокирующее ожидание
это окно не расширяет — оно у любого вызова. Не чинил по указанию владельца;
разбор для будущей правки.

## 2026-09-28 — владелец разрешил adjacent lookup после `.48`

**Прежнее решение.** В `.48` модуль принимал только явный override либо
per-user fallback: соседний файл мог бы незаметно изменить поведение внешней
библиотеки. Это ограничение было осознанным, а не техническим пробелом.

**Новые данные и решение.** В комплекте приложения `softhsm2-util` из
`tools/bin` без переменной видит общий пользовательский стор, тогда как
приложение с `SOFTHSM2_CONF` — изолированный. Владелец явно запросил
дополнительный приоритет: `SOFTHSM2_CONF` → читаемый `softhsm.conf` или
`softhsm2.conf` рядом с *загруженным модулем* → per-user. Соседний конфиг
теперь применяется и к внешнему модулю; это намеренное изменение прежнего
правила. CWD не участвует. Для `softhsm2-util` ранний статический загрузчик
должен получать путь выбранного модуля до собственной инициализации.

**Проверка.** Локальная Linux-сборка подтвердила приоритет, изоляцию
`tokens/`, alias и fallback; шесть платформ и опубликованные архивы ещё
требуют проверки.

## 2026-09-28 — владелец изменил правило конфигурации portable-модуля

**Прежняя гипотеза.** Единственный per-user конфиг для всех копий
модуля упрощает переносимость и объединяет 32-/64-битные процессы.
Поэтому с `.21` portable-сборка игнорировала `SOFTHSM2_CONF`.

**Новые данные и решение владельца.** Bundled Flutter-приложение должно
работать только со своим `softhsm.conf` и `tokens/`, не пересекаясь
с существующим пользовательским стором. Владелец 28.09.2026
явно разрешил изменить прежний публичный контракт: читаемый
`SOFTHSM2_CONF` имеет высший приоритет, иначе действует прежний
per-user режим. Относительный `directories.tokendir` привязан к
выбранному файлу. Обратная совместимость с версиями до `.21` не нужна.

**Граница.** Поиск конфигурации рядом с библиотекой предложен как
необязательный. Пока не вводить его автоматически: модуль не знает,
загружен ли он из каталога приложения или как внешняя библиотека,
а автоматический поиск у внешней библиотеки нарушил бы оговорённый
per-user fallback. Приложение само выбирает DLL и до её загрузки
может явно выставить `SOFTHSM2_CONF`.

## 2026-09-27 — Windows ARM64 OpenSSL fast-fail из-за разных CRT

## 2026-09-15 — запрет относился ко всему модулю, и под ним нашлось ещё одно

**Гипотеза** (владельца, с измерением). Один и тот же OID означает в модуле
разные кривые: ключ, выпущенный под `1.2.643.7.1.2.1.1.1`, лежит на
CryptoPro-A.

**Что сделали.** Воспроизвели независимо: четыре пары под этим OID, из двух
точек решением `y² − x³ = a·x + b (mod p)` восстановлены `a` и `b`, остальные
точки проверены на полученной кривой. Вышло `a = p − 3`, `b = 166` — это
CryptoPro-A. При интерпретации точки big-endian кривая не получается ни одна,
что заодно подтвердило little-endian `X‖Y`.

**Что показала проверка.** Причина ровно та, о которой предупреждала запись за
21.08, только запрет был написан про один файл. `BotanGOST2012KEG.cpp` задавал
домены явно, а генерация и подпись звали `Botan::EC_Group(encodedCurve)` —
запрещённым способом. Кривые различаются, но делят `p`, поэтому проверка по
длине молчала, атрибут читался обратно неизменным, а подпись и проверка
соглашались между собой, потому что обе ошибались одинаково. Спорил только
KEG.

**Вывод.** Правило «не звать `EC_Group(OID)`» бесполезно, пока живёт в
комментарии одного файла. Домены сведены в `BotanGOSTCurves`, и теперь способ
получить кривую в модуле один.

**Что нашлось под этим — дефект проверки подписи в Botan 2.19.5.** Как только
генерация перешла на настоящую paramSetA, подпись перестала проверяться
собственным же ключом. Разобрали математикой, а не догадками: выгрузили `d`,
`Q`, свёртку и подпись и проверили вручную по параметрам из RFC — `d·G = Q`,
точка на кривой, **подпись верна**. Значит ломалась проверка.

В `gost_3410.cpp` подпись считает `r = mod_order(x(kG))`, а проверка
заканчивается сравнением `R.get_affine_x() == r` — **без приведения по модулю
порядка**. Пока порядок близок к размеру поля, разница не видна: у CryptoPro-A
`q` почти равно `p`. А у TC26-кривых с кофактором 4 — 256-битной paramSetA и
512-битной paramSetC — порядок примерно вчетверо меньше поля, и `x ≥ q`
случается в трёх случаях из четырёх.

## 2026-09-14 — один неинициализированный токен прячет все остальные

**Гипотеза** (владельца, по живому прогону). Плагин не показывает устройств
вовсе не потому, что не узнаёт наш токен, а потому что видит рядом с ним
запасной неинициализированный и считает это неисправностью.

**Что сделали.** Собрали список ровно так, как его видит приложение:
`C_GetSlotList(tokenPresent = TRUE)`, затем `C_GetTokenInfo` и `C_OpenSession`
на каждом слоте.

**Что показала проверка.** При одном инициализированном токене список из двух
слотов. Слот 0 — наш токен, сессия открывается. Слот 1 — запасной,
`CKF_TOKEN_INITIALIZED` снят, `C_OpenSession` = `0xE1`,
`CKR_TOKEN_NOT_RECOGNIZED`. Достаточно одного инициализированного токена,
чтобы это случилось; вытеснить запасной из списка можно только пятнадцатью.

**Вывод.** Дефект не в токене и не в криптографии, а в составе списка.

открывается; наш список этого не гарантировал. Чинится составом списка, а не
кодом ошибки: если отвечать на запасном слоте чем-то другим вместо
`CKR_TOKEN_NOT_RECOGNIZED`, приложение всё равно получит слот, на котором
ничего нельзя сделать.

ломая. Проверено до правки и после: `--free` находит запасной слот в обоих
случаях.

**Цена, названная вслух.** На пустом хранилище профиль теперь не показывает ни
одного слота с токеном. Это верно по существу — считыватель без устройства

виден»: его заводят по номеру первого слота без токена. Два гейта опирались на
прежнее поведение и переписаны.

## 2026-09-14 — построение KEG для 512 бит: установлено по контрольным значениям TC26

**Гипотеза.** Владелец поставил вопрос прямо: какую свёртку и какой KDF
предписывает 512-битный случай, какой длины получается ключ и какого он типа —
и запретил переносить 256-битные решения по инерции. Первая догадка по обрывку
из поиска: для 512 бит KEG — это один VKO-512, без дерева KDF.

**Что сделали.** Нашли первоисточник — спецификацию расширений PKCS #11 от
TC26 — и вытащили из неё текст. В ней оказались **два готовых примера с
эталонами**: `sample_keg_256` и `sample_keg_512`, каждый с ключами сторон,
синхропосылкой и 64-байтовым `ETALON`. Это независимый известный ответ:
он опубликован органом стандартизации и посчитан не нами.

Затем перебрали построения против обоих эталонов отдельной программой на
Botan, не трогая наш код: свёртка (Стрибог-256 / Стрибог-512), наличие дерева
KDF, какая часть 32-байтовой синхропосылки идёт в VKO, порядок байт закрытого
ключа, открытого ключа и входа свёртки.

**Что показала проверка.** Ровно по одному совпадению на каждый эталон, оба —
при одних и тех же соглашениях о порядке байт:

| | 256 бит | 512 бит |
| --- | --- | --- |
| Кривая в примере | `1.2.643.7.1.2.1.1.1` | `1.2.643.7.1.2.1.2.3` (paramSetC) |
| Свёртка VKO | Стрибог-256 | **Стрибог-512** |
| KDF | `KDF_TREE`/HMAC-Стрибог-256, два блока | **нет** |
| Длина результата | 64 байта | 64 байта |
| Тип ключа в примере | `CKK_MAGMA_TWIN_KEY` | `CKK_KUZNECHIK_TWIN_KEY` |

Общее для обоих: в VKO идут **первые 16 байт** синхропосылки; умножение на
кофактор по модулю порядка; открытый ключ и вход свёртки — `X‖Y`
в обратном порядке байт. Порядок байт выведен заново, а не перенесён: он
совпал с 256-битным, но теперь это измерено, а не предположено.

Отдельно прогнали **официальный 256-битный эталон через наш собственный
модуль**: `C_CreateObject` + `C_DeriveKey(CKM_GOST_KEG)` + чтение `CKA_VALUE`
дают `ETALON` **байт в байт**. Это сильнее прежней формулировки «сверено с
независимым результатом»: наш KEG-256 совпадает с опубликованным значением
стандарта.

**Расхождение, которое при этом вскрылось.** Эталон совпадает, только если
подать `CKA_VALUE` закрытого ключа в обратном порядке байт относительно
примера: у «Рутокена» `CKA_VALUE` ГОСТ-ключа — little-endian, у нас —
big-endian. Вживую это не видно и ничего не ломает: ключ порождается на
токене и наружу сырым не выдаётся, а пара (d, Q) у нас самосогласована —
потому и работает расшифрование на живом ПО. Разница проявилась бы только при
импорте или экспорте сырого закрытого ключа, чего плагин не делает. Наш
внутренний порядок не трогаем — это 256-битный путь, который менять нельзя;
но контрольный вектор в тесте обязан подаваться с разворотом, и это должно
быть написано рядом с ним, иначе следующий читатель решит, что тест подогнан.

**Ловушка с кривыми — проверена повторно.** Botan 2.19 знает
`1.2.643.7.1.2.1.2.1` (512 paramSetA) — и его параметры **совпали** с
RFC 7836 (p, a, b, порядок, кофактор 1). А `paramSetB` и `paramSetC` Botan не
знает вовсе. Именно paramSetC нужен для официального эталона, поэтому его
параметры придётся задать явно, как уже сделано для 256-битного paramSetA.
У paramSetC кофактор 4 (m = 4q) — не 1.

**Вывод.** Вопрос закрыт по стандарту, а не по аналогии: для 512-битного
ключа KEG — это VKO-512 на Стрибоге-512, без дерева KDF, результат 64 байта,
тип — twin key. Устройственной трассы для 512-битного KEG по-прежнему нет:
что именно умеет железо, неизвестно, и выдавать это за снятое с устройства
нельзя.

односlotовый фасад. Запасной неинициализированный токен теперь виден
намеренно, значит занятых слотов два. Утверждение переписано на новый

## 2026-09-07 — единицы поля важнее алгоритма, а «честная» линейная алгебра дорога

алгоритме: в константах выработки ACPKM, в поведении счётчика на границе секции
или в самой гамме. Так обычно и бывает, и именно туда хотелось смотреть.

`поле / 8` совпало побайтно у обоих шифров; при длине секции, равной полю, —
расхождение ровно с 65-го байта.

**Вывод.** Алгоритм был верен целиком, дефект — в единицах измерения одного
поля. Проверка обеих трактовок заняла минут пятнадцать и сняла с повестки
разбор ACPKM, счётчика и гаммы. Когда поле — число, а расхождение начинается в
характерной точке (64 = 512/8), первым делом проверяется множитель, а не
математика.

**Второе, из той же задачи.** Кузнечик считал линейное преобразование по
определению — шестнадцать раундов скалярного произведения в GF(2⁸), 2304
умножения в поле на блок. Это давало 1,1 МиБ/с против 31 МиБ/с у Магмы, то есть
шифр с вдвое большим блоком работал в 28 раз медленнее. Замена на таблицы (L
линейно, значит раскладывается по байтам) дала 86 МиБ/с — в 76 раз быстрее, при
побайтно неизменном результате.

**Вывод.** Реализация «прямо по тексту стандарта» законна как определение, но не
как рабочий код: разница здесь оказалась не в проценты, а в два порядка. При
этом таблицы стоит **строить вызовом** той самой прямой реализации, а не
переписывать константы руками — тогда быстрый путь не может разойтись с
определением, и медленный остаётся в коде как его спецификация.

**Как доказали, что результат не изменился.** Отпечаток в 19 456 байт на шифр:
развёртка ключа, шифрование и расшифрование блока, CTR, OMAC и MGM в обе
стороны, на 64 разных ключах. Сравнение до и после — побайтное. Один
перевёрнутый бит в одной клетке таблицы отпечаток ловит.

## 2026-09-05 — 512 бит: три дефекта, которых чтение кода не показало

**Гипотеза.** 512-битный ГОСТ — это копия 256-битного пути с другими
размерами: параметризовать генератор по длине порядка, добавить тип ключа,
завести флаг. Задание так и было расписано, и на бумаге сходилось.

**Что показала проверка.** Генерация заработала только с третьей попытки, и ни
один из трёх отказов не был виден в коде глазами.

1. **`CKR_TEMPLATE_INCONSISTENT` уже после того, как ключ сгенерирован.**
   `P11GOSTPublicKeyObj::init` и его приватный близнец безусловно ставили
   `CKA_KEY_TYPE = CKK_GOSTR3410`. Попытка «сохранить существующий 512-битный
   тип» не помогает: на свежем объекте атрибута ещё нет, значит ставится
   256-битный, а потом шаблон с 512-битным типом с объектом не сходится.
   Правильное место — конструктор: `newP11Object` уже знает вариант, и объект
   должен получить его там. Нашлось только печатью типа атрибута, который
   отверг обновление (`0x100`, то есть `CKA_KEY_TYPE`); статический разбор
   уводил в `extractObjectInformation` и `saveTemplate`, где причины не было.
2. **`CKA_KEY_GEN_MECHANISM` всегда 256-битный.** Записывался константой, так
   что 512-битный ключ утверждал бы, что порождён 256-битным механизмом.
   Дефект тихий: ни один вызов из-за него не падает.
3. **Вставка в таблицу механизмов разрезала чужой `#ifdef`.** Строка
   `t["CKM_GOSTR3410_512_KEY_PAIR_GEN"]` со своими `#endif`/`#ifdef` попала
   внутрь блока `WITH_GOST_3410_2012_256`, и
   `CKM_GOSTR3410_WITH_GOSTR3411_2012_256` уехал под 512-битный флаг. Скобки
   сошлись, сборка прошла, и в сборке с одним 256-битным флагом механизм
   совместной подписи просто исчез бы. Поймано перечитыванием guard-ов после
   правки, а не компилятором.

**Вывод.** Текстовые правки по образцу «вставить рядом» опасны там, где рядом
стоят директивы препроцессора: они балансируются, но меняют принадлежность
соседних строк. И отладочная печать в двух местах дала ответ за один прогон
там, где чтение кода потратило несколько заходов и не дало ничего — при
непонятном коде возврата дешевле собрать инструментированный модуль, чем
рассуждать. Для этого в песочнице поднято отдельное быстрое дерево сборки
поверх уже собранных Botan и OpenSSL: пересборка тридцать секунд вместо
четырёх минут.

**Отдельно про вектор Стрибога-512.** Первый прогон известного ответа не
сошёлся, и причиной была не реализация, а моя транскрипция: сообщение M1
вышло 62 байта вместо 63. Вектор после этого взят из самого RFC 6986, а
порядок байт проверен перекрёстно — разворот печатного 256-битного результата
RFC даёт значение, уже сверенное в этом репозитории. Совпадение
256-битного случая и было доказательством, что разворот применён правильно.

## 2026-08-22 — принудительный экспорт не требует отладочного ABI модуля

**Исходная гипотеза.** Для выгрузки sensitive/non-extractable ключа отдельной
утилите всё равно понадобится нестандартная публичная функция в PKCS #11
модуле либо собственный парсер файлового хранилища.

**Что сделали.** `softhsm2-export` слинкована со статическим ядром SoftHSM и
работает с тем же `Configuration`, `SlotManager`, `ObjectStoreToken`, сессиями,
логином и расшифрованием приватных атрибутов, что и модуль. Единственный
внутренний метод обхода атрибутов закрыт compile-time определением, которое
получают статическая библиотека и экспортёр, но не shared-модуль. Сырые файлы
хранилища утилита не разбирает и не пишет.

**Что показала проверка.** RSA и P-256 EC, импортированные штатным
`softhsm2-util` с `CKA_SENSITIVE=true` и `CKA_EXTRACTABLE=false`, восстановлены
в PKCS #8, валидны для независимого OpenSSL и имеют те же публичные ключи.
`nm -D` подтверждает отсутствие `exportPrivateKey` в shared-модуле.

**Вывод.** Для программного тестового токена можно иметь явный отладочный
escape hatch без изменения стандартного PKCS #11, без скрытого vendor ABI и
без дублирования формата хранилища. Цена — экспортёр содержит отдельную
статическую копию ядра и обязан собираться теми же опциями и backend, что
модуль; portable workflow теперь обеспечивает это из одной CMake-конфигурации.

**Первый CI-отказ не относился к экспорту.** В контейнерной job Actions
использовал для нового шага `/bin/sh`, несмотря на то что скрипт написан под
bash и начинает с `set -euo pipefail`; dash отказал на самой первой строке.
Вывод для inline-скриптов тот же, что для файловых: если используется bash
синтаксис, shell должен быть указан явно, окружение runner это не гарантирует.

**Второй отказ был специфичен для статической сборки Windows.** На Linux и
macOS `C_GetFunctionList` из статического ядра разрешился напрямую, а MSVC
скомпилировал его объявление как `__declspec(dllimport)` и искал
`__imp_C_GetFunctionList`. Это не дефект самого ядра: `cryptoki.h` уже имеет
предусмотренный режим `CRYPTOKI_STATIC`, но новая цель его не включила.
Определение добавлено только экспортёру в CMake и Automake. После этого все
три Windows-архитектуры собрали статический executable, а shared-модуль так и
не получил отладочный ABI. Вывод: связь со статической Cryptoki-библиотекой на
Windows требует не только правильной `.lib`, но и статического режима её
публичных объявлений.

## 2026-08-21 — умолчание `CKA_EXTRACTABLE` и цена этого решения

**Находка владельца.** Производный VKO-ключ выходит нечитаемым. ПО задаёт в
шаблоне только `CKA_CLASS`, `CKA_KEY_TYPE` и `CKA_TOKEN`, значит остальное
берётся из умолчаний модуля, и значение потом не прочитать.

**Что оказалось при разборе.** Формулировка находки указывала на
`CKA_SENSITIVE`, но он у нас **уже** `false` по умолчанию. Отказ даёт
`CKA_EXTRACTABLE`: его умолчание `false`, а проверка `ck7` в
`P11Attribute::retrieve` отвергает значение при `isSensitive() ||
!isExtractable()`. Заодно выяснилось, что общая ветка `C_DeriveKey` (та, куда
попал бы VKO) `CKA_SENSITIVE`/`CKA_EXTRACTABLE` от базового ключа **не
наследует** — только `CKA_ALWAYS_SENSITIVE` и `CKA_NEVER_EXTRACTABLE`. То есть
производный ключ получает ровно умолчания модуля, и правка нужна ровно одна.

**Решение владельца и его цена.** Я предложил три объёма: только производные
ключи, все секретные, все включая приватные. Владелец выбрал третий и делать
сразу, не дожидаясь замера с устройства. Возражение было высказано до правки и
записывается здесь, потому что оно не снимается выбором:

- приватный ключ ГОСТ или RSA, созданный из шаблона, который про это молчит,
  теперь отдаёт своё секретное значение по `C_GetAttributeValue` и может быть
  завёрнут `C_WrapKey`;
- настоящий Рутокен так не делает, то есть это **осознанное расхождение с
  эталоном** — первое, которое мы вносим намеренно, и оно противоречит правилу
  «устройство эталон», записанному в `AGENTS.md` днём раньше. Правило
  сохраняется для того, что модуль *сообщает* о себе; здесь изменено то, что он
  *хранит*, и владелец счёл размен приемлемым.

Что **не** изменилось: шаблон, который явно просит `CKA_SENSITIVE=CK_TRUE` или
`CKA_EXTRACTABLE=CK_FALSE`, получает именно это, и обратно ни то ни другое не
поворачивается. Значение поменяло только молчание. Гейт `core-behaviour`
проверяет обе стороны — и что молчаливый шаблон даёт читаемый ключ, и что
явная просьба даёт нечитаемый, — так что «умолчание» не выродится в
«единственное поведение». Отрицательным прогоном проверено: возврат умолчания
в `false` роняет гейт на `CKA_EXTRACTABLE has an unexpected value`.

**Чего мы так и не измерили.** Что ставит ключам сам Рутокен, когда шаблон
молчит. Утилита это уже умеет (второй аргумент — PIN, логинится и печатает
`CKA_SENSITIVE`/`CKA_EXTRACTABLE`/`CKA_VALUE readable?` по каждому ключу), но
владелец решил не ждать. Если замер разойдётся с тем, что мы поставили, менять
придётся здесь же — одно умолчание в `P11AttrExtractable::setDefault`.

## 2026-08-21 — значимые изменения теперь публикуются без ручного запуска

**Предыдущее решение.** 14 августа автоматический workflow научили собирать и
проверять шесть платформ, но публикацию намеренно оставили ручной: номера тегов
выбирались человеком. Это решение и его причины ниже в журнале не удаляются.

**Новое решение владельца.** После каждого значимого изменения публичный
релиз должен появляться сам; просить владельца отдельно запускать тот же полный
workflow больше нельзя. Чистая правка проектной документации новой версией
продукта не считается.

**Реализация.** После шести verifier jobs workflow сравнивает проверенный
`workflow_run.head_sha` с последним `v2.7.0-portable.N`. Пути проектной
документации отфильтровываются; любой оставшийся путь включает публикацию.
Следующий номер вычисляется по максимуму всех числовых portable-тегов. Если
автоматически выбранный тег уже существует, workflow падает вместо
перезаписи. Ручной запуск сохранён как аварийный путь и только он умеет
обновлять явно названный релиз.

**Почему классификация находится в release job.** Сигнал `workflow_run`
нельзя отфильтровать по путям, не потеряв правило «полностью собирать транк
после любого изменения». Поэтому docs-коммит всё ещё проходит шесть сборок и
шесть проверок; отсекается только лишний публичный тег.

**Первый живой отказ и причина.** Прогон `32491184165` успешно собрал и
проверил 6/6 платформ, но release job упала сразу после `git fetch --tags`.
Причина не в тегах и не в правах: Actions запускает bash с `-e -o pipefail`, а
конвейер `git tag … | head -n 1` заставляет `git tag` получить `SIGPIPE`, когда
`head` закрывает чтение. Присваивание из такого конвейера имеет ненулевой код и
останавливает скрипт. `head` заменён на `sed -n '1p'`: результат тот же, но
`sed` дочитывает поток, так что ложного отказа нет. Это закрепляет правило для
workflow-скриптов: локальную проверку конвейеров запускать с теми же
`-e -o pipefail`, что использует Actions.

**Второй живой отказ и причина.** После исправления конвейера прогон
`32494259369` прошёл 6/6 сборок и 6/6 независимых проверок, а шаг выбора тега
дошёл до проверки предка. Там обнаружилась отдельная проблема: стандартный
`actions/checkout` оставлял release job с shallow-историей только текущего
коммита. Теги были загружены, но полной цепочки между `.25` и проверяемым
коммитом не было, поэтому `git merge-base --is-ancestor` штатно вернул 1.
Release checkout теперь использует `fetch-depth: 0`. Для логики, которая
сравнивает коммиты или проверяет ancestry, одной загрузки тегов недостаточно.

**Живое подтверждение положительного пути.** Прогон `32497429071` на
`eaf42cc` прошёл 6/6 сборок, 6/6 независимых проверок и release job. Без
ручного запуска создан `v2.7.0-portable.26`. Тег указывает точно на проверенный
SHA; 12 опубликованных ZIP скачаны обратно, и все записи `SHA256SUMS`
совпали. Два предыдущих отказа были fail-safe: до исправления ни существующий
релиз, ни его assets не изменялись.

**Живое подтверждение отрицательного пути.** Чистый docs-коммит `a7ed597`
прошёл CI и полный portable-прогон `32500403362`: 6/6 сборок и 6/6 verifier
jobs успешны. Release job перечислила только `AGENTS.md`, `HANDOFF.md` и
`docs/*`, вывела `publication skipped` и не запускала ни один шаг подготовки
или публикации assets. Latest остался `.26`; `.27` не существует.

## 2026-08-21 — вызов плагина оказался KEG, а OID Botan — не той кривой

**Исходная гипотеза.** В трассе расшифрования механизм `0xD4321039` получает
40-байтовую структуру, похожую на ГОСТ-параметры согласования, и создаёт ключ
типа `0xD4321007`. По одному дампу это можно было принять за очередной вариант
`CKM_GOSTR3410_12_DERIVE` и самостоятельно придумать структуру.

**Что подтвердили.** Официальные заголовки и примеры двух обёрток Рутокен
называют `0xD4321039` именно `CKM_GOST_KEG`; его ABI — стандартная
`CK_ECDH1_DERIVE_PARAMS` с `CKD_NULL`, 32 байтами синхропосылки и 64 байтами
открытого ключа. Результат — `CKK_MAGMA_TWIN_KEY`, которому в отдельном
пространстве типов ключей тоже присвоено `0xD4321007`. Численное совпадение с
`CKM_GOSTR3410_12_DERIVE` не связывает эти две константы.

**Неожиданная причина неверного результата.** Первая реализация использовала
`Botan::EC_Group` по OID TC26 256 paramSet A и не совпала с независимым
контрольным результатом. Botan 2.19.5 сопоставляет этот OID со старой
CryptoPro-A: обе кривые 256-битные, поэтому поверхностная проверка проходит,
но точки и порядок различаются. Настоящая TC26 paramSet A имеет cofactor 4 и
255-битный порядок. Для этого OID группа теперь строится из явных параметров;
арифметика и ослеплённое умножение остаются в Botan.

**Порядок байтов.** KEG сначала разворачивает первые 16 байт синхропосылки,
затем VKO читает результат little-endian. При загрузке в big-endian `BigInt`
две перестановки взаимно уничтожаются; дополнительный разворот давал другой
секрет. Нулевой UKM остаётся отдельной веткой спецификации.

**Проверка.** Сквозной вызов `C_DeriveKey` совпал по всем 64 байтам с
независимым результатом VKO + `KDF_TREE_HMAC_Streebog256`, затем прошёл с
точным трёхатрибутным шаблоном плагина. Неверный KDF возвращает
`CKR_MECHANISM_PARAM_INVALID`. Полные `prepare` и `rutoken-profile` прошли на
сборке с минимальным Botan 2.19.5.

**Вывод.** Для криптографии недостаточно, чтобы библиотека «узнала» OID:
контрольный результат должен проверять саму доменную группу и все соглашения о
порядке байтов. Следующий шаг расшифрования нельзя угадывать заранее — нужна
новая трасса после первого успешного KEG.

## 2026-08-21 — `small` — это макрос MSVC, и зелёный push-CI этого не видит

**Что случилось.** Релизный прогон на `50e1f49` упал — три Windows-проверки из
двенадцати джоб, все на шаге сборки тест-кита:

```
portable-token-e2e.cpp(2633): error C2628: 'CK_ULONG' followed by 'char'
                              is illegal (did you forget a ';'?)
```

Строка была `CK_ULONG small = length - 1;`. У MSVC `windows.h` дотягивается до
`rpcndr.h`, где `#define small char`, и объявление перестаёт быть объявлением.
Та же ошибка лежала второй раз — в `rutoken-reference-dump.c`, чей заголовок
обещает сборку через `cl`.

**Почему не поймали раньше.** Push-CI собирает сквозной клиент только
Linux-компилятором. Проверял ли бы это mingw, который стоит локально?
Проверили: **нет**. У mingw `windows.h` до `rpcndr.h` не доходит, `small` там
не определён, и битая версия компилируется без замечаний. Значит гейт на mingw
дал бы ложную уверенность, и добавлять его не стали.

**Вывод про процесс, он же главный.** Сеть безопасности сработала: релизный
workflow идёт автоматически после каждого зелёного CI, собирает шесть платформ
и покраснел. Не сработал я — отчитался «CI зелёный» и не посмотрел прогон,
который этот же CI и запускает. **Зелёный `ci.yml` не означает, что продукт
собирается: MSVC участвует только в релизном прогоне.** После пуша в `main`
надо дожидаться и его, а не только `ci.yml`.

**Вывод про код.** Имена из `windows.h` — отдельный класс ловушек, и ловятся
они только настоящим MSVC. Кроме `small` в наших исходниках из известного
набора (`hyper`, `boolean`, `interface`, `near`, `far`, `OPTIONAL`,
`GetObject`, `GetMessage`, …) чисто; единственный `interface` — в апстримном
`C_GetInterface`, и он MSVC уже много релизов проходит. `max` в клиенте взят в
скобки, `(std::numeric_limits<...>::max)()`, — от того же семейства.

## 2026-08-21 — трёх атрибутов нет и у настоящего Рутокена

**Гипотеза.** Отчёт по Центру управления: приложение читает `0x80003010`,
`0x8000800E` у объекта аппаратной особенности и `0x80000009` у сертификата,
получает отказ и считает это ошибкой. Значит у нас три пробела, и надо снять
значения с устройства и добавить их. Отчёт даже проверил гипотезу
подстановкой: с этими тремя атрибутами Центр управления доходит до конца
стартового цикла без единого неуспешного вызова.

**Что сделали.** Вместо того чтобы спрашивать три адреса, научили
`rutoken-reference-dump` мести весь диапазон `0x80003000`..`0x80003012` плюс
`0x8000800D/E` **по одному атрибуту** — в общем вызове один отсутствующий
атрибут прячет судьбу остальных, — и заодно читать вендорские атрибуты
сертификата. Владелец прогнал на устройстве.

**Что показала проверка.** Из трёх «пробелов» не подтвердился ни один:

- `0x80003010` — устройство отвечает `CKR_ATTRIBUTE_TYPE_INVALID`, ровно как
  мы. То есть Центр управления получает этот отказ и от настоящего Рутокена.
- `0x80000009` и `0x80003304` у сертификата — тоже отсутствуют у устройства.
  Второй заодно закрывает отложенный пункт 5 предыдущего отчёта: работы там
  нет вовсе.

Зато метёлка нашла **восемь** атрибутов, которых у нас не было и о которых
никто не спрашивал: `0x80003002`, `0x8000300A`, `0x8000300C`..`0x8000300F`,
`0x80003011`, `0x80003012` — и девятый, `0x8000800E`, который спрашивали.
Итого у объекта двадцать атрибутов вместо одиннадцати.

**Вывод.** «Приложению стало легче» и «так делает устройство» — разные
критерии, и подстановка проверяет первый, выдавая себя за второй. Здесь они
разошлись: добавить три атрибута значило бы отвечать там, где эталон
отказывает, то есть уехать от устройства ради того, чтобы приложению было
приятнее. Отказ по `0x80003010` теперь закреплён в гейте отдельной проверкой —
именно потому, что выглядит как наша недоделка и его будет тянуть «починить».

Второй урок, дешёвый: спрашивать надо не то, чего не хватает по чужому списку,
а весь диапазон. Стоило это одного прогона и дало восемь недостающих значений
сверх задачи.

**Заодно сверено с устройством:** `C_EX_GetTokenName` совпал во всех трёх
формах — запрос размера, чтение, короткий буфер (`0x150` и длина всё равно
проставлена). Правка не понадобилась.

## 2026-08-20 — даты приватных объектов: запись и чтение шли разными путями

**Источник.** Третий отчёт владельца: на `ra.rutoken.ru` всё ломалось сразу
после первой генерации ключа через Рутокен Плагин — «Подписание» отвечало
«Неизвестная ошибка», экран сертификатов тоже. В трассе на этом месте
`C_GetAttributeValue(CKA_START_DATE) → CKR_GENERAL_ERROR`. Один такой ключ
отравлял весь экран, потому что плагин читает срок действия у каждого.

**Причина, и она апстримная.** Атрибуты приватного объекта хранятся
зашифрованными на ключе токена (`IV(16) || AES-256-CBC`).
`P11Attribute::updateAttr` шифрует, `P11Attribute::retrieve` расшифровывает —
но `P11AttrStartDate::updateAttr` и `P11AttrEndDate::updateAttr` базовый метод
**переопределяли** и клали значение как есть; параметры `token` и `isPrivate`
у них были даже закомментированы. Восемь байт `CK_DATE` расшифровать нельзя:
`SecureDataManager::decrypt` отрезает первые 16 байт как IV, их там нет, и
чтение падает. Дефект спал, пока даты никто не задавал: пустое значение обе
ветки пропускают. Прямое `osobject->setAttribute(type, ByteString(...))`
встречается в файле ровно два раза — оба в этих классах.

**Воспроизведено** на портируемом модуле **с выключенным профилем**, то есть
это чистый SoftHSM, а не наша надстройка: приватный ключ с датами —
`rv=0x005`, открытый — `0x000`; `C_SetAttributeValue` на существующем ключе
ломает его так же.

**Миграция.** Ключи, у которых даты уже лежат открытым текстом, после правки
превратились бы в нечитаемый шифртекст. Различить эти два случая можно без
догадок: шифрование выдаёт 16 байт IV плюс минимум один 16-байтовый блок AES,
то есть **никакой шифртекст не бывает короче `CK_DATE`**. Значит блоб ровно в
`sizeof(CK_DATE)` — это старое открытое значение, и читать его надо как есть.
Проверено: старое хранилище исправленным модулем читается, старым — нет.

**Чем это едва не осталось непроверенным.** Первый отрицательный прогон
показал зелёный гейт с **восстановленным** дефектом. Причина не в гейте:
миграционная поблажка честно читает открытое значение обратно, поэтому через
PKCS #11 испорченная запись неотличима от исправной. Отличие остаётся только
в том, что дата приватного ключа лежит на диске открытым текстом — срок
действия ключа виден в файле токена без PIN. Гейт научили смотреть туда:
приватному ключу пишутся даты, непохожие на публичные, и в файлах хранилища
их быть не должно. С восстановленным дефектом гейт после этого падает с
указанием файла.

**Вывод.** Когда правка добавляет совместимость со старыми данными, эта
поблажка заодно маскирует и сам дефект. Проверять в таком случае надо не
наблюдаемое поведение, а то свойство, ради которого правка делалась.

## 2026-08-20 — блокирующий `C_WaitForSlotEvent`

**Задача.** Центр управления Рутокен держит отдельный поток слежения за
устройством и получал `CKR_FUNCTION_NOT_SUPPORTED`: первая строка
`SoftHSM::C_WaitForSlotEvent` отвергала всё, кроме `CKF_DONT_BLOCK`. Владелец
попросил сделать это для форка целиком, а не только для профиля.

**Две вещи, которые определили решение.**

- **Ждать на мьютексе PKCS #11 нельзя.** Приложение вправе передать свои
  функции блокировок через `C_Initialize`; они умеют захватить и отпустить, но
  не «поспать до события». Поэтому ожидание сделано на `std::condition_variable`
  — это внутренняя синхронизация, наружу она не видна. `pthread_cond_*` в
  модуле и так уже слинкованы (через OpenSSL), новых зависимостей нет.
- **`C_Finalize` уничтожает синглтон** (`SoftHSM::reset()`). Разбудить
  спящего, чтобы сообщить ему именно об этом, — половина смысла вызова, значит
  то, на чём он спит, обязано пережить объект. Состояние вынесено в статический
  объект вне класса, а сама ожидающая функция — свободная, чтобы после
  пробуждения ничего не трогало уже разрушенный `this`.

**Событие в SoftHSM действительно есть.** Апстримный комментарий утверждал,
что слоты не меняются. Но библиотека всегда держит один запасной слот с
неинициализированным токеном, и `C_InitToken` на нём — это появление токена
там, где его не было; следующий `C_GetSlotList` отдаёт список на слот длиннее.
Именно это и сообщается. Повторная инициализация существующего токена стирает
его, но ничего не вставляет, и событием не считается.

**Проверено** отдельной программой: `pSlot == NULL` → `CKR_ARGUMENTS_BAD`;
тишина → `CKR_NO_EVENT`; `C_InitToken` на запасном слоте даёт ровно одно
событие с верным номером слота; блокирующий вызов действительно спит (0.30 с) и
просыпается на следующем событии; `C_Finalize` отпускает спящего с
`CKR_CRYPTOKI_NOT_INITIALIZED`; второй одновременный блокирующий вызов
получает `CKR_FUNCTION_FAILED`, как требует стандарт. В сквозной гейт вошло
всё, кроме двух случаев с потоками: если событие уже лежит в очереди,
блокирующая форма отвечает сразу, и это проверяет тот же вход без гонки.

## 2026-08-20 — объект аппаратной особенности снят с устройства

**Гипотеза.** Одиннадцать вендорских атрибутов, которые Рутокен Плагин читает
с `CKO_HW_FEATURE`, из программного токена не выводятся: их надо снять с
железа и отдавать как есть.

**Что сделали.** Дополнили `tests/portable/rutoken-reference-dump.c` дампом
этого объекта — спрашивает ровно как плагин, одним вызовом с заранее
выделенными буферами, и печатает сырые байты. Владелец прогнал её на
устройстве.

**Что показала проверка.**

- **Длины не восемь, а `sizeof(CK_ULONG)`.** Плагин выделяет под каждый
  не-булев атрибут восемь байт, и мы записали восьмёрку как часть контракта.
  Устройство отвечает четырьмя — на Windows `CK_ULONG` четырёхбайтовый.
  Больший буфер и более короткий ответ — это нормальный `C_GetAttributeValue`,
  и раз плагин так работает с железом, работает и с нами. В гейт добавлен
  именно этот случай: восьмибайтовый буфер, ответ длиной `sizeof(CK_ULONG)`,
  хвост буфера не тронут.
- **`0x8000800D` существует и равен нулю.** Атрибута нет в опубликованных
  заголовках Aktiv 2.19 и 2.21, и мы держали открытым вопрос, отдавать его
  или отвечать `CKR_ATTRIBUTE_TYPE_INVALID`. Устройство отдаёт один байт со
  значением 0 — вопрос снят фактом.
- **Догаданные имена интерфейсов не подтвердились.** Мы записали в `rutoken.h`
  `NFC = 0x02`, `BLUETOOTH = 0x04`, `ISO = 0x08` по здравому смыслу.
  Устройство сообщает маску поддерживаемых `0x21`, где второй бит — `0x20` —
  ни одним из этих имён не объясняется. Имена убраны, остался
  подтверждённый `TOKEN_INTERFACE_USB = 0x01`, маска хранится сырой.

**Вывод.** Тот же урок, что и с серийником: угаданное значение и снятое с
устройства выглядят одинаково правдоподобно ровно до первой проверки. Держать
в заголовке имя, которого никто не подтверждал, хуже, чем не иметь имени
вовсе, — потому что следующий читатель примет его за факт. Отрицательным
прогоном (подменили `0x21` на `0x01`) убедились, что гейт эти значения
действительно стережёт, а не просто их перечисляет.

## 2026-08-20 — что показала трассировка Рутокен Плагина

**Источник.** Отчёт владельца: Рутокен Плагин 4.12.2.0 против портируемого
модуля с включённым профилем, 723 стандартных вызова PKCS #11 плюс трейл
`C_EX_*`. Первоисточник, а не рассуждение.

**Главное, что узнали.** Плагин принимает профиль за Рутокен ECP целиком:
находит устройство, логинится, перечисляет ключи и сертификаты, разбирает
ГОСТ-сертификат, строит CMS и CAdES и подписывает. Из 34 функций расширения
он трогает три. CMS и PKCS #10 плагин собирает сам, а токен просит только
подписать 32 байта — то есть остальные 30 функций расширения для
совместимости с ним реализовывать не нужно. Это экономит много работы.

> **Уточнено 14.09.2026:** функций не три, а две —
> `C_EX_GetFunctionListExtended` и `C_EX_GetTokenInfoExtended`; остальные 32
> плагин не зовёт. Запись оставлена как есть: так тогда прочитали трассу.
> Разбор — в записи за 14.09.2026.

**Серийник оказался не BCD.** Плагин печатает
`getDeviceInfo(TOKEN_INFO_SERIAL) = 1968268439` там, где `C_GetTokenInfo` даёт
`75516497`, а `1968268439` = `0x75516497`. Значит поле `serialNumber[8]` — это
двоичное число big-endian, а восьмисимвольная строка — его hex. По нашему
эталонному устройству различить было нельзя: у него в серийнике одни цифры, и
BCD даёт те же байты. Кодек переведён на hex; на цифровом серийнике результат
тот же, но буквы `a`–`f` он теперь переживёт.

**Два отказа, которые ломали плагин, и оба — наши.** `C_DigestInit` отвергал
DER-OID набора параметров, который библиотека Aktiv принимает и который плагин
шлёт всегда: ломался весь `digest()`. `C_GenerateKeyPair` требовал
`CKA_GOSTR3411_PARAMS`, которого плагин не шлёт, и отвергал вендорский
`CKA_VENDOR_KEY_JOURNAL`, который шлёт в каждом шаблоне: не работал
`generateKeyPair()`, единственный способ завести ключ из веб-приложения.

**Тонкость, на которой правка едва не осталась половинчатой.** Подставить
набор параметров в локальную переменную мало: объект открытого ключа строится
из шаблона вызывающего, а не из этих переменных, поэтому без явной вставки в
шаблон он создавался бы без атрибута, обязательного для своего класса, и вызов
всё равно падал бы с `CKR_TEMPLATE_INCOMPLETE`. Ловится это только прогоном
настоящей генерации — что и показала проверка на GOST-сборке: первая версия
правки дала ровно тот же код возврата, что и до неё.

**Чем проверено.** Программой из приложения к отчёту, которая воспроизводит
шаблон плагина дословно, и своей — она дополнительно требует, чтобы чужой
набор параметров, неверная длина и обрезанный OID по-прежнему отвергались, а
хеш с параметром и без совпадал байт в байт. Оба прогона на портируемой сборке
с ГОСТ, не на урезанной.

## 2026-08-14 — автозапуска релизной сборки не было никогда

**Гипотеза владельца.** Раньше портируемый релиз собирался автоматически после
зелёного CI, а потом это где-то отключилось.

**Что показала проверка.** Прошёл по всем ревизиям `portable-release.yml` в

никогда, отключать было нечего.

**Что сделали.** Добавили то, чего не хватало: `workflow_run` на успешное

проверяет шесть платформ, ручной вдобавок публикует релиз. Публикацию оставили
ручной намеренно: теги нумеруются вручную и не переиспользуются, автопубликация

тринадцати `checkout` проставлен `github.event.workflow_run.head_sha`.

**Проверено на живом прогоне.** Первый автоматический запуск — `31807829226`,

x64/ARM64, Windows x86/x64/ARM64, macOS universal) и шесть проверок на чистых
раннерах — все зелёные; джоба публикации `skipped`, как и задумано. Полный
цикл — около 29 минут. Заодно это первая проверка расширения `C_EX_*` на
нативном MSVC: три Windows-сборки прошли.

**Цена, о которой стоит помнить.** Полный цикл запускается и на коммитах,
которые трогают только документацию: `workflow_run` не умеет фильтровать по
путям, а фильтровать по путям сам `CI` нельзя — тогда пропадёт сигнал «транк
зелёный». Пока принято как есть.

## 2026-08-14 — что на самом деле проверял пуш-CI

**Вопрос.** Почему после правок в коде не пересобрался портируемый релиз.

**Что показала проверка.** Релиз и не должен был: у `portable-release.yml`

было покрытие. По решению владельца `ci.yml` теперь собирает клиента и гоняет

что именно джоба исполняет, а не только её цвет.

## 2026-08-14 — вендорское расширение `C_EX_*`

**Гипотеза.** Часть ПО не опознаёт модуль как рутокеновский, потому что у него
нет второй таблицы функций: у Рутокена рядом со стандартной есть расширение,
и его наличие проверяют.

**Как добыли описание.** Rutoken SDK — 485 МБ. Скачивать целиком не пришлось:
сервер поддерживает range-запросы, поэтому по концу файла прочитана
центральная директория zip, а из неё вытянуты девять заголовков
`sdk/pkcs11/include/`. Скрипт остался в песочнице, хеши файлов записаны в
`docs/RUTOKEN-EXTENSIONS.md`.

**Что показала проверка.** Расширение — это `CK_FUNCTION_LIST_EXTENDED`:
`CK_VERSION`, затем 34 указателя в фиксированном порядке. Точка входа
`C_EX_GetFunctionListExtended` устроена как `C_GetFunctionList` и обязана
работать до `C_Initialize`.

**Вывод и решение.** Заголовки Aktiv в репозиторий не копируются: ABI объявлен
своими словами в `src/lib/pkcs11/rutoken.h`, приложения по-прежнему подключают
заголовки вендора. Таблица отдаётся всегда — флаг профиля читается в
`C_Initialize`, то есть позже, чем эта функция должна ответить, а скрыть
экспорт всё равно нельзя. Смысловой ответ даёт только
`C_EX_GetTokenInfoExtended`, и он гейтится профилем. Все 34 поля таблицы
заполнены: `NULL` роняет вызывающего, который берёт указатель по смещению.

**Что осталось нечестным и было закрыто в тот же день.** Больше половины
`CK_TOKEN_INFO_EXTENDED` описывает железо, которого у нас нет. Владелец снял
показания с эталонного устройства — они подставлены вместо догадок, см.
`docs/RUTOKEN-EXTENSIONS.md`. Заодно выяснилось, что структура на Windows
занимает 164 байта, а на Linux 256, и наша раскладка сошлась с вендорской: их
библиотека приняла наш `sizeof` и вернула его же.

**Главная находка: серийник в расширенной структуре — BCD, а не число.**
Печатному `47738461` соответствуют байты `00 00 00 00 47 73 84 61`, то есть по
две десятичные цифры в байте. Мы писали туда двоичное значение
(`02 D8 6E 5D`) — приложение, читающее поле как BCD, показало бы мусор.
Исправлено; сквозной гейт проверяет именно эту раскладку, и проверка не
декоративная: с возвращённой ошибкой упаковки он падает.

> **Уточнено 20 августа:** «BCD» — вывод по одному образцу, и он неверен.
> Поле двоичное, big-endian, а печатная строка — его hex; на серийнике из
> одних цифр обе трактовки дают одни и те же байты, поэтому различить их на
> этом устройстве было нельзя. Разобрала трассировка Рутокен Плагина, см.
> запись за 20 августа.

**Что ещё разошлось с догадками.** Номер протокола `0x01` (гадал `0x20`),
микрокод `0x1E` (гадал `0x18`), номер заказа `2` (гадал `0`), PIN-коды 6..249
у обоих (гадал 6..32), ATR — 15 реальных байт с «Rutoken DS» внутри (гадал
пустой), контрольная сумма прошивки `0x4D27D7A2` при **не** выставленном
`FW_CHECKSUM_UNAVAILIBLE` (гадал наоборот), батарея — не нули, а `0xFFFFFFFF`
в проценте и флагах при нулевом напряжении. Флагов `SUPPORT_FKN` и
`SUPPORT_SECURE_MESSAGING` у эталона нет, хотя я их заявлял. Совпало немного:
тип и класс токена, объём памяти, счётчики попыток, цвет корпуса. Вывод тот
же, что и с механизмами: правдоподобное — не то же самое, что верное.

## 2026-08-13 — константы профиля `FAKE_RUTOKEN_ECP` сверены с эталонным устройством

**Источник.** Вывод `pkcs11-tool -I`, `-T` и `-M` с реального
`C:\Windows\System32\rtPKCS11ECP.dll` (владелец). Это первоисточник; всё, что
до него бралось из чужих опубликованных выводов, перепроверено по нему.

**Совпало и не трогалось.** `C_GetInfo` целиком: Cryptoki 2.40,
`Aktiv Co.`, `Rutoken ECP PKCS #11 library`, версия библиотеки 2.19. Далее
`manufacturerID` = `Aktiv Co.`, `model` = `Rutoken ECP`, PIN 6/249. Флаги и
размеры ключей всех RSA-механизмов, включая границу 768 для SHA-384/512.

**Исправлено по эталону.**

- Версия железа 60.1 и прошивки 30.2 — было 67.4 и 34.2.
- Серийный номер: восемь **десятичных** цифр (`47738461`), было восемь
  шестнадцатеричных, то есть с буквами.
- Флаги токена: `login required, rng, token initialized, PIN initialized` и
  ничего больше. Убраны безусловные `CKF_SO_PIN_TO_BE_CHANGED` и
  `CKF_USER_PIN_TO_BE_CHANGED` — они сообщали, что токен непригоден, пока не
  сменят PIN-коды.
- Размеры ключей EC: `ECDSA-KEY-PAIR-GEN` и все `ECDSA*` — ровно 256..256,
  `ECDH1-DERIVE` — 255..512. Было 256..521 и 255..521.

**Ошибка, исправленная тем же заходом.** Перед получением эталона описание
слота было изменено на `Aktiv Rutoken ECP 00 00` по чужому опубликованному
выводу с Linux. Эталонное устройство печатает `Aktiv Rutoken ECP 0` — то, что
и было изначально. Возвращено. Вывод на будущее: опубликованные чужие выводы
годятся для гипотез, но не для констант.

**Расхождения, закрытые следом (решение владельца от 13 августа).** Раньше
профиль показывал пересечение списка устройства с тем, что реализовано, и
всегда подменял метку. Владелец решил иначе: список механизмов должен
совпадать с устройством в точности, включая нереализованное, потому что часть
ПО судит о совместимости по одному только списку, а остальные механизмы
планируется дореализовать. Сделано:

- все 70 механизмов устройства в его порядке, с его размерами ключей и
  флагами; вызов нереализованного даёт `CKR_MECHANISM_INVALID` из самой
  операции, а механизм, которого у устройства нет, отвергается так же;
- `GENERIC-SECRET-KEY-GEN` — как на устройстве: 80..2048,
  `generate, generate_key_pair, derive`;
- метка: пустая у токена — показываем `Rutoken ECP <no label>`, как устройство;
  заполненная — показываем её, как требует стандарт.

**Как это проверено.** Таблица в `SoftHSM.cpp` и таблица-эталон в
`verifyRutokenProfile` выведены скриптом из сырого вывода `pkcs11-tool -M`
владельца, а не набраны руками. Сверка модуля с этим эталоном — 70 из 70,
порядок, размеры и флаги совпадают. Обе ветки правила о метке проверены
отдельно. Побочный эффект, который стоит помнить: список заодно управляет
`isMechanismPermitted`, поэтому при включённом профиле недоступно то, чего нет
у устройства (например, EdDSA).

## 2026-08-13 — относительный путь к модулю и порядок поиска DLL на Windows

**Что случилось.** На стенде владельца `pkcs11-tool --module .\softhsm2.dll -I`
давал `CKR_GENERAL_ERROR`, а с абсолютным путём работал. Причина оказалась вне
проекта: в системных каталогах лежали посторонние копии `softhsm2.dll`, и
загружалась одна из них. После их удаления всё заработало.

**Что стоит знать.** У `LoadLibrary` относительный путь — не «файл в текущем
каталоге». По документации Microsoft полный путь ищется только по нему, а
относительный **подставляется в каждый каталог списка поиска**, начиная с
каталога исполняемого файла и включая `System32` — который при штатном safe DLL
search mode просматривается раньше текущего каталога. Поэтому `.\module.dll`
может загрузить совсем не тот файл, который лежит рядом.

Практический вывод для нашей поставки: модуль стоит указывать абсолютным путём.

**Что сделали по итогам.** Укрепили `get_user_path()` на Windows — к этому
инциденту отношения не имеет, но чинит реальную хрупкость:

- значения берутся из блока окружения процесса (`GetEnvironmentVariableA`), а
  копия CRT идёт вторым мнением: статически слинкованный рантайм внутри DLL
  держит собственный снимок;
- дальше `HOMEDRIVE` с `HOMEPATH`, последним — профильный каталог от шелла
  (`SHGetFolderPathA`), подгружаемый по требованию, без статического импорта;
- устранено молчаливое усечение: было `snprintf` в `char[512]` без проверки, и
  длинный `%USERPROFILE%` давал не короткий путь, а другой и неверный;
- при полном провале печатается перечень испробованных источников.

Проверено на Linux и на Windows x64.

**Заодно проверено на нативном Windows x64** (раннер `windows-2025`): пять форм
пути к модулю против `-I`, `-T` и `-M` — пятнадцать случаев, ноль отказов.

## 2026-08-12 — юнит-тесты не исполняются в CI

**Гипотеза.** Зелёный транк означает, что тесты проходят.

**Что сделали.** Прошли поиском по всем workflow: `make check`, `ctest`,
`cppunit`, `test-suite.log`.

**Что показала проверка.** Ни одного вхождения. `ci.yml` после переработки под
портируемую сборку содержит одну джобу — сборку зависимостей и аудит архива.
Цели ctest при этом в проекте зарегистрированы (`enable_testing()`,
`add_test` в восьми каталогах `test/`) и собираются локально, а в autotools
живёт `TESTS = cryptotest`. То есть тесты существуют и исполнимы, но CI их не
вызывает. Заодно выяснилось, что форк правил
`src/lib/object_store/test/ObjectStoreTests.cpp` — файл, который с тех пор ни
разу не исполнялся автоматически.

**Вывод.** «Зелёный транк» в этом репозитории означает «портируемый архив
собирается и проходит аудит», и ничего не говорит о юнит-тестах. Прогон CI сам
по себе не подтверждает правку в тестах или в криптокоде — до восстановления
прогона проверять такие изменения локально через `ctest`.
