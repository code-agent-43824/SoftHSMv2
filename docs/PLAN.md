Пункты ниже до первого `[x]` — решения владельца от 29.09 по режиму

- [ ] **PIN сверяется с копией, прочитанной при загрузке токена.**
      `Token::Token` (`src/lib/slot_mgr/Token.cpp:54–65`) читает блобы PIN в
      `SecureDataManager` один раз, а `Token::loginUser` (`:205–229`) и
      `Token::loginSO` (`:181–202`) сверяют с этой копией и файл токена не
      перечитывают. Наблюдение владельца 29.09 на программном стенде: процесс
      A открыл модуль, процесс B сменил user PIN через `C_SetPIN`; в A новый
      PIN даёт `CKR_PIN_INCORRECT`, старый — `CKR_OK`, до перезапуска A.
      Воспроизведено 30.09 на `.54` под профилем, и вдобавок каждая неудачная
      попытка A с верным новым PIN списывается с **общего** счётчика: его
      видит свежий процесс, так что A может заблокировать PIN всем. Сам
      счётчик уже хранится в токене и перечитывается в транзакции при каждом
      входе (`.53`, JOURNAL за 29.09); расходится только копия PIN. Нужно
      сверять PIN с состоянием токена на момент `C_Login`, чтобы смена сразу
      действовала во всех процессах, как на устройстве, где PIN проверяет само
      устройство. SO PIN кешируется так же (по коду, не проверялось).
      Подтвердить на эталоне: A открыл сессию → B сменил PIN → A входит новым
      и старым PIN.
- [ ] **Заводские PIN должны выглядеть заводскими.** Решение владельца 29.09
      заменяет решение от 14.08. Токен с заводскими PIN — user `12345678`,
      SO `87654321` — не получает `TOKEN_FLAGS_USER_PIN_NOT_DEFAULT` и
      `TOKEN_FLAGS_ADMIN_PIN_NOT_DEFAULT` в `C_EX_GetTokenInfoExtended`; после
      смены PIN соответствующий флаг ставится. Сейчас флаги выводятся из
      `CKF_TOKEN_INITIALIZED` и `CKF_USER_PIN_INITIALIZED`
      (`src/lib/SoftHSM.cpp:1148–1152`) и стоят на любом инициализированном
      токене — на стенде 28.09 клиентское ПО прочитало так заводские
      `12345678`/`87654321` как сменённые (JOURNAL за 28.09). Значение PIN
      известно только в момент установки — `C_InitToken`, `C_InitPIN`,
      `C_SetPIN`, — поэтому признак вычислять там и хранить в токене.
- [ ] **PIN короче 6 символов — `CKR_PIN_LEN_RANGE`.** Профиль объявляет
      минимум 6 для обоих PIN, значит установка или смена более короткого
      PIN должна отвечать `CKR_PIN_LEN_RANGE`, если устройство не покажет
      другой код. С `.53` это уже почти так. Проверено 30.09 на `.54` под
      профилем: `C_InitPIN` и `C_SetPIN` с PIN из 5 символов и `C_InitToken`
      с SO PIN из 5 символов отвечают `CKR_PIN_LEN_RANGE`. Границу даёт
      политика токена — в `C_InitPIN`, `C_SetPIN` и, для `C_InitToken`, в
      `Token::createToken` (`src/lib/slot_mgr/Token.cpp:413–414`); от
      профиля эти проверки не зависят (по коду, без профиля не проверялось).
      Осталось одно: `C_InitToken` с SO PIN короче 4 символов отвечает
      `CKR_PIN_INCORRECT`, потому что раньше срабатывает проверка по
      `MIN_PIN_LEN = 4` (`src/lib/SoftHSM.cpp:2364–2366`,
      `CMakeLists.txt:81`). `C_Login` длину не проверяет: PIN из 3–5
      символов даёт `CKR_PIN_INCORRECT` и списывает попытку (на `.54`: 10 → 9
      → 8 → 7). Тратит ли такая попытка счётчик на устройстве — снять вместе
      со счётчиком (пункт «Снять на эталонном устройстве счётчик попыток PIN»).
- [ ] **`utcTime` в `C_GetTokenInfo` — пустое.** Сейчас туда пишется текущее
      UTC-время (`src/lib/slot_mgr/Token.cpp:599–604`), хотя
      `CKF_CLOCK_ON_TOKEN` не ставится. Каким байтом заполнено пустое поле —

      `tests/portable/rutoken-reference-dump.c` это поле не выводит

      устройства и только потом менять модуль.
- [ ] **Снять KEG на 512-битных ключах с эталонного устройства.** Владелец
      29.09: KEG на 512-битных ключах может работать на эталоне; поведение

      устройстве, `C_DeriveKey` с `CKM_GOST_KEG` на открытом ключе второй

- [x] **Гонка `C_WaitForSlotEvent` с `C_Finalize` — исправлена (слово
      владельца 30.09).** Механизм — `docs/JOURNAL.md` за 29.09: проверка
      `isInitialised` и запоминание `epoch` в `awaitSlotEvent` не атомарны
      относительно `endSlotEventEpoch()`, и ждущий пропускает пробуждение.
      Правка: состояние событий само знает, открыта ли библиотека.
      `C_Initialize` открывает эпоху, `endSlotEventEpoch()` закрывает её под
      тем же замком, а `awaitSlotEvent` под замком отвечает
      `CKR_CRYPTOKI_NOT_INITIALIZED`, если эпоха закрыта, и лишь потом
      запоминает `epoch`. Регрессионный тест в `p11test`: много раз
      `C_Initialize`, блокирующий вызов в потоке, сразу `C_Finalize`;
      каждый вызов обязан вернуться. Готово, когда харнесс из JOURNAL
      проходит без зависаний, `ctest` зелёный и `.54` проверен.
      Тест `InfoTests::testWaitForSlotEventFinalizeRace` вскрыл вторую
      сторону гонки — падение (`docs/JOURNAL.md` за 30.09), поэтому правка
      шире плана: `C_WaitForSlotEvent` идёт мимо `SoftHSM::i()` через
      `SoftHSM::waitForSlotEvent`. Код внесён; локально `ctest` 7/7,
      `p11test` 10/10, харнесс 3 × 50 000 итераций без зависаний.
      Выпущено в `v2.7.0-portable.54` (`313f0bc`) и проверено: 13/13 джоб,
      12 ZIP по `SHA256SUMS`, тест-кит Linux x64, харнесс на опубликованном
      модуле 2 × 50 000 без сбоев, на опубликованном `.53` — падение.

## Замечено по дороге, не реализовано

- [ ] **Отмена релизного прогона может застать публикацию.** `concurrency`
      в `portable-release.yml` отменяет весь прогон, включая `release`: так
      `.49` опубликован прогоном `36431044973` с итогом `cancelled`. В тот раз

      каждого прогона сверять список релизов, а не только итог.

- [ ] **`CKM_GOSTR3410` и `CKM_GOSTR3410_512` не принимают набор параметров
      хеша.** Они подписывают готовую свёртку и ничего не хешируют, так что
      набор их не описывает — граница проведена намеренно. Но если найдётся

      блокером. Расширять политику только по трассе, не «на всякий случай»:
      придумывать приём без данных — то же самое, что придумывать константу.
      Место правки одно — ветка по умолчанию в

- [x] **Расшифрование после KEG — закрыто трассой от 14.09.2026.** Ждали
      трассу, чтобы не гадать, какой механизм плагин выберет после
      `C_DeriveKey`. Трасса есть, и ответ оказался проще ожидаемого:
      **никакого**. Ни `C_UnwrapKey`, ни `C_Decrypt` плагин не зовёт.

      Фактическая последовательность:
      `C_DeriveKey(CKM_GOST_KEG, CK_ECDH1_DERIVE_PARAMS{kdf = CKD_NULL,
      ukm 32 байта, открытый ключ 64 байта}, шаблон из трёх атрибутов:
      `CKA_CLASS`, `CKA_KEY_TYPE = 0xD4321007`, `CKA_TOKEN = False`)` →
      `C_GetAttributeValue(CKA_VALUE)` запросом длины, ответ 64 →
      `C_GetAttributeValue(CKA_VALUE)` за самими 64 байтами →
      `C_DestroyObject`. Дальше плагин расшифровывает в софте на добытом
      ключе. Новых функций PKCS #11 не нужно — ни одной.

      **Отсюда следует то, что легко сломать не заметив:** читаемость
      `CKA_VALUE` у выработанного ключа критична. Ключ приходит с молчаливым
      шаблоном — про `CKA_SENSITIVE` и `CKA_EXTRACTABLE` в нём не сказано
      ничего, — и если выдать его нечитаемым, расшифрование перестанет
      работать целиком. `RUTOKEN_FORCE_SENSITIVE` на выработанные KEG-ключи
      поэтому не распространяется.

      **Границы:** зашифрование CMS плагин делает в софте на открытом ключе
      получателя — новых функций PKCS #11 для него тоже не нужно.
