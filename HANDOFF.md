# HANDOFF — незавершённое прямо сейчас

Обновлено: 2026-08-12.

## В работе

Этап 6 — проверка на реальном стенде. Владелец прогнал сборки Windows x86, x64
и ARM64 на Windows 11 ARM в Parallels (MacBook Air M5). x86 и ARM64 чисты.

**Дефект Windows x64: относительный путь к модулю ломает `C_Initialize`.**
`pkcs11-tool --module .\softhsm2.dll -I` → `CKR_GENERAL_ERROR` (`0x5`); тот же
вызов с абсолютным путём работает. Обходной путь: абсолютный путь. Механизм не
установлен — из исходников не выводится, наш код в портируемой сборке путь
модуля вообще не читает. Полный ход разбора в `docs/JOURNAL.md`.

Воспроизвести отказ агент не может: Windows и ARM-стенда нет, весь разбор
получен чтением кода и данными владельца.

## Точный следующий шаг

Нужно решение владельца — работа приостановлена, не заблокирована.

Дефект локализован: ломается только Windows x64 **под эмуляцией** на ARM64,
при относительном пути к модулю. Обходной путь работает — передавать модуль
абсолютным путём. Причина не установлена.

Диагностическая сборка **не годится**: на Windows логирование молчит.
Определение `DEBUG_LOG_STDERR` есть в `softhsm_common.vcxproj`, но строки
`SOFTHSM_DIAG_LOG` в собранной DLL нет, и принудительный отказ не пишет ни в
консоль, ни в файл. На Linux та же цепочка работает. Артефакт отдавать
владельцу нельзя: он напечатает пустоту.

Три варианта, по убыванию стоимости:

1. Чинить прибор дальше — следующий шаг понятен: печатать не факт наличия
   строки `DEBUG_LOG_STDERR` в `.vcxproj`, а саму матчнувшуюся строку, чтобы
   увидеть, в какой это секции и в какой конфигурации.
2. Ограничиться обходным путём: задокументировать в `README.txt` портируемой
   поставки, что модуль надо указывать абсолютным путём, и закрыть тему.
3. Копать на стенде владельца отладчиком — там единственная машина, где
   дефект живой.

## Диагностическая ветка

`claude/diag-windows-x64-module-path`, в `main` не идёт. Содержит: правку
`scripts/portable/build-windows.ps1` (флаги под `PORTABLE_DIAGNOSTIC_LOG=1` и
ворота на их наличие), дублирование лога в файл по `SOFTHSM_DIAG_LOG` в
`src/lib/common/log.cpp`, автономный загрузчик `scripts/portable/diag-load.c`
с обёрткой сборки, и одноразовый workflow `diag-windows-x64.yml`,
срабатывающий на push в эту ветку.

Загрузчик рабочий и полезен сам по себе: печатает разрешённый путь модуля,
текущий каталог и `USERPROFILE`/`HOMEDRIVE`/`HOMEPATH` глазами CRT процесса.

## О чём знать следующему агенту

- Тест-кит вызывает `pkcs11-tool` только с `-I` и `-T`. Всё остальное
  поведение утилиты автоматикой не покрыто.
- CI подменяет `USERPROFILE` на временный каталог, поэтому права и содержимое
  настоящего `%USERPROFILE%\softhsm` не проверяются никогда.
- Юнит-тесты не запускаются ни одним workflow, и это осознанное решение
  владельца. Правки в `src/lib/**/test/**` и в криптокоде проверяйте локально:
  `cmake -S . -B build && cmake --build build --parallel && ctest --test-dir build --output-on-failure`.
