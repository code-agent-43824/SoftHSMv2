# HANDOFF — незавершённое прямо сейчас

Обновлено: 2026-10-19.

## Ждёт владельца: единая интерактивная проба

По запросу владельца в PLAN внесены два исправления, для которых
аппаратных данных уже хватает: результат `CKM_GOST_KEG` типа
`CKK_KUZNECHIK_TWIN_KEY` и атрибуты сгенерированного по шаблону SDK ключа
ГОСТ 28147. Их реализация — отдельный следующий шаг. Проба оставшихся
механизмов собрана и локально проверена: исходник
`tests/portable/rutoken-derive-probe.c`, инструкция
`tests/portable/README-gap-probe.txt`, комплект
`/workspace/rutoken-gap-probe-20261019-linux-x64.zip`.
CI и публикация `v2.7.0-portable.88` прошли; скачанный Linux x64 пакет
сверен с `SHA256SUMS` и проверен по CRC. Запуск диагностического бинарника:
`./rutoken-gap-probe --interactive`; путь модуля, слот и PIN вводятся в
терминале, PIN скрыт. Программа пишет один лог с отметками разделов 1–16.
Владелец присылает полный лог, включая `Done.`; если запуск аварийно
завершится, достаточно частичного лога и последних строк терминала.
Отказы отдельных механизмов — диагностические ответы, а не сбой пробы.
После аппаратного лога сверить результаты с JOURNAL и закрыть
подтверждённые случаи; пока не приписывать неизвестным KDF/VKO алгоритм.

## Ждёт проверки владельца: VKO в `.87`

Полный лог Linux x64 пробы получен и разобран (JOURNAL 19.10). Три
подтверждённых расхождения `CKM_GOSTR3410_12_DERIVE` исправлены:
UKM 1–32 байта, `CKD_CPDIVERSIFY_KDF` с 512-битным ключом и
`CKA_VALUE_LEN=16/64` для результата `CKK_GOST28147`. Локальная сборка,
сквозной `prepare` и диагностическая проба прошли. CI и семь
платформенных проверок скачанных пакетов прошли; исправление выпущено в
`v2.7.0-portable.87`. Скачанный Linux x64 архив проверен по контрольной
сумме и CRC (STATUS). На устройство исправленный модуль не запускался.
Следующий шаг — проверка `.87` в ПО владельца, особенно W7/W8 плагина.

Селектор VKO `0xD4321026` работает на устройстве, но его алгоритм пока
не установлен; простое хеширование результата `CKD_NULL` не совпало.
Два прямых KDF и отдельный VKO-512 требуют принимаемого примера вызова;
проверенные в пробе варианты не дали его. У сгенерированного по образцу
SDK ключа ГОСТ 28147 остаются отличия атрибутов. Точные следующие шаги —
в PLAN; не подменять неизвестную семантику предположением.

## Ждёт владельца: W7/W8 Рутокен Плагина после `.84`

Часть 2 `CKM_GOSTR3410_12_DERIVE` выпущена в `v2.7.0-portable.84`.
`device-parity` на реальном Рутокене 17.10 прошёл, включая новый кейс `vko`:
значения двух сторон, типы и атрибуты результата, UKM 4/16/32,
`CKD_CPDIVERSIFY_KDF`, 512-битные пары и коды отказа. Дополнительно прошёл
`device-parity-write`. Сырой разбор — JOURNAL 18.10. По этим логам
расхождений для исправления модуля нет.

**Следующий шаг.** Дождаться сценариев W7/W8 плагина на стенде владельца
(`code-agent-43824/extension2`): расшифрование ГОСТ 28147-89 без ошибки
147, итоговый текст совпадает. Если сценарий не пройдёт, нужны сырой лог
вызовов PKCS #11, версия плагина и входные данные для воспроизведения;
сверить фактический вызов с проверенным `vko` прежде, чем менять код.
Проба 19.10 расширила проверенные длины UKM и подтвердила
`CKD_CPDIVERSIFY_KDF` с 512-битным ключом. Импорт закрытого ГОСТ-ключа
и `CKM_GOSTR3410_DERIVE` не расширять предположениями.

## Открыто, но не в работе

- **Позднее закрытие на macOS и Windows** — исправлено и проверено на Linux
  (`.76`); другие платформы владелец проверит позже (PLAN). Тест там сначала
  должен упасть на `.75`.
- **Версии `C_GetSlotInfo`** — минор на будущее по слову владельца 16.10:
  профиль отдаёт слоту 67.4/34.2 по аналогии с токеном, а у устройства
  версии слота где-то есть, где-то нулевые. Без сырого вывода
  `C_GetSlotInfo` с устройства по каждому слоту не править (PLAN).
- **Байты `85[4..7]` записи журнала** — нулевая заглушка по решению владельца
  11.10, что это у устройства, не установлено.
- **SQLite `multi-token`**: порядок слотов сбивается, потому что
  `CKA_OS_TOKENCREATED` нет в таблице типов `DBObject` (JOURNAL 12.10).
  Портируемые сборки SQLite не включают; не исправлено.
